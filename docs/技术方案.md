# 技术方案

**版本：** v1.0
**日期：** 2026-08-11
**AI：** Codex

## 架构

`Client -> protocol adapter -> priority router -> configured upstream`

- OpenAI Responses：`POST /v1/responses`
- OpenAI Chat Completions：`POST /v1/chat/completions`
- Anthropic Messages：`POST /v1/messages`、`POST /v1/messages/count_tokens`
- 三种适配器只负责路径、认证头、可选的旧配置模型覆盖和 SSE 事件边界；不做协议内容转换。
- Anthropic 适配器移除客户端的 `Authorization` / `x-api-key`，向上游发送当前 Provider Key；同时发送标准 `x-api-key` 与网关兼容的 Bearer 认证，缺少 `anthropic-version` 时补 `2023-06-01`。
- `anthropic-beta` 等非敏感协议头原样保留。

实现采用 Python 3、`httpx` 与标准库 SQLite：单进程承载兼容代理、状态 API 和轻量管理页。服务只绑定 loopback 地址，运行数据保存在项目本机数据库中。

## 状态模型

每个 provider 保存：`enabled`、`priority`、`upstream_url`、`protocol`、可选的旧配置 `forced_model`、`cooldown_until`、`last_error`、`last_success_at`、`last_latency_ms`。Provider 列表、凭据和运行状态统一保存在项目本机 SQLite，不再依赖写死的五项。

## Provider 管理接口

- `POST /api/providers`：新增名称、API 地址和 key，协议默认为自动匹配，默认使用客户端请求模型，并排到队尾。
- `PUT /api/providers`：改名或换 key；空 key 保持原值，改名同步运行状态和当前 Provider。
- `DELETE /api/providers`：删除 Provider、运行状态和本地 key；历史请求记录保留原名称。
- SQLite 数据库目录权限固定为仅本机用户可访问；状态响应仅返回 `has_key` 和 `key_hint`，其中 `key_hint` 为前6位、后4位，中间使用省略号。

## 可观测请求模型

- 代理保存客户端原始模型 `requested_model`，并以 `model` 保存实际发送给上游的模型；新增渠道默认二者相同，旧渠道存在模型覆盖时才会不同。
- 每条成功、失败、超时、网络错误和 SSE 早期失败事件都写入这两个字段；旧 JSONL 事件没有字段时由前端显示 `-`。
- 前端在模型列显示实际模型；当两者不同时显示 `requested_model → model`，用于确认是否误请求 `luna`。

## 上下文能力观测

- 代理为每个传入请求生成短 `request_id`，同一次故障转移尝试的事件共享该 ID；不保存请求正文或响应正文。
- 以结构化请求 JSON 生成输入 token 估算值，仅用于线路观测，不作为精确计费数据。
- Provider 运行状态累计 `max_success_input_tokens` 和 `min_context_failure_tokens`；前者表示已验证的历史成功下限，后者只表示曾出现上下文错误的样本，不直接宣称线路固定上限。
- 不主动发送每日超长探测请求，避免额外费用和供应商风控；后续可基于真实请求逐步扩大观测范围。
- 已知历史基线：P3 成功 `364,127` 输入 token，P5 成功 `349,395`，P4 成功 `325,945`；这些证据表明当前没有足够依据认定某条线路存在明显更低的固定上下文窗口。

## 国际化

- 语言资源位于 `src/web/locales/en.json` 和 `zh-CN.json`，构建时复制到 `dist/web/locales/`。
- 浏览器用 `navigator.languages` 判断系统是否包含中文；不包含时默认英文。
- 手动选择写入 `localStorage` 的 `switchLocalProxy.locale`，支持 `system`、`en`、`zh-CN`。
- 构建验证会比较语言 key 集与占位符，并固定校验品牌名和语言原生名称。
- 英文基线由 Tongyi Qwen / DashScope 生成，再按紧凑运维界面语境人工校正。

## 版本更新检查

- 仓库根目录的公开 `version.json` 是唯一版本源，`run.sh build` 将其复制到 `dist/version.json`，使已安装版本可离线读取自身版本。
- `UpdateChecker` 仅在管理页请求 `GET /api/update` 时启动后台检查；成功结果写入本机 `runtime/update.json` 并缓存 24 小时，失败状态仅缓存 15 分钟。
- 拉取目标固定为公开 GitHub `version.json`，2 秒超时并使用不含安装信息的通用 User-Agent；请求不含认证、Cookie、Provider 信息或事件数据。
- `/api/update` 只返回 `state`、当前/最新版本、公开更新链接和检查时间。拉取异常返回 `unavailable`，不参与路由、冷却、日志事件或健康检查。

## 请求记录分页

- 状态接口返回内存中保留的最近 200 条脱敏事件，前端按时间倒序分页，不额外请求提示词或响应数据。
- 可选每页数量为 10、20、50、100，默认 20；保存在 `localStorage` 的 `switchLocalProxy.eventPageSize`。
- 新事件到达、记录清空或总页数变化时，当前页会自动约束在有效页码范围内。

## 流式重试边界

上游 HTTP 2xx 不一定代表成功。代理在向客户端提交 SSE 前缓冲初始事件：OpenAI 若先出现 `error` 或 `response.failed`，Anthropic 若先出现 `event: error` / `type: error`，均判为失败并尝试下一 Provider。OpenAI 的输出 delta/completed 或 Anthropic 的 content/message delta/stop 出现后立即转发；之后不重试，避免重复生成。

事件判断按 SSE `event:` 行和 `data:` JSON 的精确类型执行；Chat Completions 额外识别 `choices[].delta`、`choices[].message` 和 `finish_reason`，不对生成文本做子串匹配。

## 本机请求边界

- 无 `Origin` 的本机 CLI 请求保持兼容；带 `Origin` 的浏览器请求只接受 loopback 来源，或与当前本机 Host 别名一致的来源（例如 `p.a.com`）。
- 请求体上限为 16 MiB，连接读取超时为 30 秒。
- `Cookie`、客户端认证头与本机来源头不作为上游凭据；Provider Key 由代理注入。
- 上游错误在持久化和返回前对 `sk-` 凭据做不可逆脱敏。
- 本地代理不要求客户端携带 API Key；它忽略客户端认证头并按当前 Provider 从本机 SQLite 注入上游认证。因此 CC Switch 的本地条目应生成 `requires_openai_auth = false`，避免让用户填写无意义的占位密钥。

## 协议范围提示

Provider 是路由凭据，不是“GPT Key”或“Claude Key”的绑定项。管理弹窗以固定提示说明支持 OpenAI Responses、OpenAI 兼容 Chat Completions 与 Anthropic Messages；请求路径决定使用哪一个适配器。原生 Gemini `generateContent` 不在支持范围内。供应商或 Key 不支持其中一类协议时，该次请求按正常失败/故障转移处理。

## 发布隐私门禁

`support/privacy_scan.py` 检查跟踪文件、未忽略的新文件、所有 Git 历史 blob 和 `dist/` 明确白名单。检查覆盖 Provider Key、常见平台令牌、私钥、个人绝对路径、邮箱、未批准 URL、数据库、日志、运行目录和浏览器快照；报告只包含类别、文件与行号。

安装健康检查通过后，`run.sh install` 会清理后台解释器生成的 `dist/__pycache__/`，避免运行时文件进入发布包。

## 502 同线路短重试

- HTTP 502 可能是瞬时网关或上游认证链路异常。代理在未向 Codex 返回任何内容前，等待 1 秒并在同一 Provider 上重试 1 次。
- 首次 502 只写本机运行日志，不增加 Provider 失败次数、不触发冷却，也不生成一条独立失败事件。
- 第二次仍为 502 时，才记录一次失败、进入现有冷却并按优先级切到下一 Provider；503、429、超时和语义失败不增加同线路重试。
- 最终事件保存 `retry_count`，管理页在请求模型下显示重试次数。限制为一次可控制额外延迟和潜在重复计费风险。
- 输入 token 估算只统计 JSON 中的文本值；内嵌 `image_url` / `file_data` 二进制内容按附件占位处理，避免 base64 体积被误算成文本上下文。
- 估算器带内部版本号；升级到附件感知算法时只清空旧的上下文观测最大/最小值，不修改 Provider 成功/失败次数、优先级、开关或冷却状态。
- 新事件保存 `input_estimator_version=2`；旧事件继续保留，但管理页不再展示其不可比的输入估算值。

上下文窗口错误由 `is_context_error` 识别。它会写入请求记录并更新上下文观测值，但 `cooldown_until` 保持为 0，不把 Key 熔断。代理仍可继续尝试其它 Provider；如果全部候选都返回同类错误，最终响应为 `400 context_length_exceeded`。

## 运行与发布

- 源码目录：当前仓库根目录
- 本机运行状态：项目内已忽略的 `runtime/`
- 守护：`~/Library/LaunchAgents/com.switch-local-proxy.plist`
- 回滚：恢复 `~/.codex/config.toml` 的原 `15721` 地址。
- 自检：`./run.sh doctor` 校验运行依赖、JSON 配置、key 权限、LaunchAgent、服务身份与可用渠道。
- 修复：`./run.sh repair` 重新测试、构建和安装；安装前备份上一份 `dist` 与 plist，新版本健康检查失败时自动恢复。
- macOS 兼容：若 `launchctl bootstrap` 在已登录的图形会话返回 `Input/output error`，安装脚本会先确认服务是否已经加载；未加载时回退到同一用户域的 `launchctl load -w`，随后仍执行健康检查。
- 容错：损坏的数值状态回退到安全默认值；所有 JSON 与 key 更新使用原子替换，LaunchAgent 对后台服务始终保活，手动停止时先禁用再终止。
- SQLite 的连接上下文只负责事务，不会自动关闭连接；所有数据库读写必须再用 `contextlib.closing` 显式关闭，避免长期运行耗尽文件描述符。
- 第二个 LaunchAgent `com.switch-local-proxy.watchdog` 通过 `StartInterval=15` 调用已验证的 Python 解释器执行无窗口健康检查；连续两次健康失败（间隔 3 秒）才执行主任务 `enable`、必要时 `bootstrap`、随后 `kickstart -k`，避免瞬时抖动中断长响应。它不承载请求流量，也不读取 SQLite 或密钥。

## 风险

- 全部上游返回 503 时，本地代理也只能明确报 503，不能恢复上游容量。
- SSE 早期预检会在极端慢首包时增加首字节等待；实现中需设定上限并记录原因。
- 本机 SQLite 损坏或没有有效渠道时，启动时需要给出无凭据的配置错误提示。

## SQLite 存储与独立渠道

- `runtime/proxy.sqlite3` 存储渠道、密钥、全局设置、运行状态和最近 200 条请求记录；数据库与日志、缓存一起被隐私门禁拒绝进入 `dist` 与 Git 历史。
- 每个渠道拥有独立的 `upstream_url`、`protocol`、来源策略和 GPT 模型策略；`auto` 协议允许全部已支持的本地路径。界面不接受手输模型名。
- 客户端路径决定本地适配器；代理把本地 `/v1` 之后的路径追加到该渠道 API 前缀。例如本地 `/v1/messages` 会追加为渠道地址的 `/messages`。
- 服务监听 `0.0.0.0` 以支持用户显式授权的局域网或指定网段客户端，但管理页面、状态接口和写接口通过客户端源 IP 强制只允许 loopback。模型路径先按渠道来源策略校验，再读取请求正文。
- 全局来源默认 `local`；渠道默认 `inherit`，明确的渠道策略优先于全局。CIDR 规则经 `ipaddress` 标准化，最多 20 条。
- 全局 GPT 防护仅改写 `gpt-*` 请求；渠道选择 `client` 策略后原样使用客户端模型，允许支持 Luna 的中继正常工作。
- Anthropic Messages 是透传适配；若上游只实现 OpenAI Responses，Claude Code 请求仍会失败，需要独立的协议转换层。
